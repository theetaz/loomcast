# @loomcast/db

Drizzle schema, SQL migrations, the client factory, the migration runner and the test-database
harness for Loomcast. The package is consumed as TypeScript source.

| Import | Contents |
|---|---|
| `@loomcast/db` | `createDb`, `migrate`, `MIGRATIONS_FOLDER`, every table, enum and row type, `kbSearch`, `nextVersionNo`, `nextFormatVersionNo`, `nextSkillVersion`, `enqueueTask`, `claimDueTasks`, `extendLease`, `completeTask`, `retryTask`, `consumeOAuthState`, `consumeOAuthConnection`, `purgeExpiredOAuth`, `latestPostMetrics`, `KB_FIXTURES`, `seedKb` |
| `@loomcast/db/schema` | Tables, pg enums and row types only |
| `@loomcast/db/testing` | `setupTemplate` and `createTestDb` for vitest |

## Schema conventions

- Tables live in `src/schema/`, one file per area. Property names are camelCase; SQL names are
  snake_case and written out explicitly (`text("password_hash")`).
- Every table has `created_at timestamptz not null default now()` (`createdAt()` in
  `src/schema/columns.ts`). Timestamps are `timestamptz` and read as `Date`.
- pg enums are built from the value arrays in `@loomcast/contracts` (`src/schema/enums.ts`).
  Never copy the values here.
- Index and constraint names are explicit: `<table>_<columns>_uq` for unique indexes, `_idx`
  for other indexes and `_ck` for checks. Tests and the API match on these names.
- Each table file exports `XRow` (select) and `NewXRow` (insert) types. The `Row` suffix keeps
  them apart from the API shapes of the same name in `@loomcast/contracts`.

## Using the client

```ts
import { createDb } from "@loomcast/db";

const { db, pool, close } = createDb(databaseUrl, { max: 10 });
// ...
await close();
```

## Migrations

Migrations are SQL files in `migrations/`, generated by drizzle-kit from the schema and committed.
They are **append-only**: once a migration is on `main`, never edit, rename or delete it. Fix
mistakes with a new migration.

1. Change the schema in `src/schema/`. To add an enum value, add it to the array in
   `@loomcast/contracts` first.
2. Generate the migration with a short descriptive name:

   ```bash
   pnpm --filter @loomcast/db exec drizzle-kit generate --name add_kb_entries
   ```

   `pnpm db:generate` works too but picks a random name.
3. Read the generated SQL. drizzle-kit cannot express everything (extensions, generated
   `tsvector` columns, data backfills). For those, edit the new file before it is merged, or
   create an empty one with `drizzle-kit generate --custom --name <name>` and write the SQL
   yourself.
4. Run `pnpm db:generate` again: it must report "No schema changes".
5. Apply it with `pnpm db:migrate`, then run the tests.

**New enum values.** drizzle-kit adds a value with `ALTER TYPE ... ADD VALUE`. Postgres refuses
to use a value added by a transaction that has not committed yet, and the migrator applies every
pending migration in **one** transaction. So keep the `ADD VALUE` statements in a migration of
their own, and never use a new value (in a default, a check, an index predicate or an update)
in any migration that may run in the same batch. Compare as text instead, as
`api_tokens_job_id_ck` does with `kind::text = 'job'`. Index predicates are the exception: they
must be immutable and an enum-to-text cast is not, so a partial index can only compare a value
the enum type was created with (as the assets dedupe indexes compare `asset_status` 'failed',
created by `0007` and recreated by `0013`), never a value added by `ADD VALUE`.

**Hand-edited statements.** drizzle-kit cannot mark a foreign key `DEFERRABLE`, and it emits
foreign keys before the unique indexes that composite keys reference. Migrations `0005` to `0007`
are edited by hand to create the indexes first and to append `DEFERRABLE INITIALLY DEFERRED` to
the current-version keys. The snapshots do not record deferrability, so a later migration that
drops and recreates one of these keys must add the clause again.

**Extensions and functions.** `pg_trgm` and the `lc_tags_text(text[])` function are created by
`0002_add_kb_tables`, written by hand above the generated statements; drizzle-kit does not track
them.

`pnpm db:migrate` reads `DATABASE_URL` (from the environment, or from the repository's `.env`),
applies pending migrations under an advisory lock and records them in
`drizzle.__drizzle_migrations`. Running it again is a no-op. Code can do the same with
`migrate(url)`.

Other scripts: `pnpm db:studio` opens drizzle-kit studio on `DATABASE_URL`, and
`pnpm --filter @loomcast/db seed:dev` creates a sample workspace for the first owner account and
fills its knowledge base with the 30 entries in `src/fixtures/kb.ts`. The seed never creates
users; create the owner with `pnpm admin:create` first. Rerunning it skips entries that are
already there (dedupe keys `seed:<key>`).

## Versioned records

Formats, content items and skills keep their content in immutable version rows
(`format_versions`, `content_versions`, `skill_versions`) numbered from 1 per parent, and the
parent always points at its current version (`current_version_id` is never null).

- **Current-version keys.** `formats_current_version_fk`, `content_items_current_version_fk` and
  `skills_current_version_fk` reference `(parent_id, id)` of the version table, so the current
  version must belong to the parent. They are `DEFERRABLE INITIALLY DEFERRED`: generate both ids
  in the application, insert the parent and its version 1 in one transaction (parent first,
  because the version's own `item_id`/`format_id`/`skill_id` key is immediate), and the check
  runs at commit. A missing version fails the commit with `23503`.
- **Numbering.** Inside the transaction that writes a version, call `nextVersionNo(tx, itemId)`
  (or `nextFormatVersionNo`, `nextSkillVersion`). It locks the parent row with `SELECT ... FOR
  UPDATE`, then reads the highest number in a second statement, and returns the next number, or
  null when the parent does not exist. Keep the default READ COMMITTED isolation. The lock is held
  until the transaction ends, so compare `current_version_id` with the client's base version after
  calling it.
- **Same parent.** `content_versions.parent_version_id` and `reviews.version_id` must be versions
  of the same item (composite keys `content_versions_parent_version_fk` and `reviews_version_fk`),
  and a series' format must belong to the series' workspace (`series_format_fk`).
- **Idempotent job results.** `content_versions_job_id_uq` allows one version per job. Store a job
  result with ``onConflictDoNothing({ target: contentVersions.jobId, where: sql`job_id is not null` })``,
  or treat `23505` on that constraint as "already stored".
- **Assets.** Uploads are deduplicated per owner. `assets_workspace_id_item_id_kind_sha256_uq`
  keeps one pending or ready asset per item, kind and SHA-256 (lowercase hex, `assets_sha256_ck`),
  so two items may each hold the same voice take or render and a version always points at its own
  item's asset. `assets_workspace_id_kind_sha256_uq` does the same per workspace for the
  workspace's own media (`item_id` null, such as reference media). Failed assets are left out of
  both so an upload can be retried. Insert-or-skip with `target: [workspaceId, itemId, kind, sha256]`
  and ``where: sql`item_id is not null and status <> 'failed'` ``, or
  `target: [workspaceId, kind, sha256]` and ``where: sql`item_id is null and status <> 'failed'` ``;
  or leave the target out. `meta` holds `{ probe?, alignment? }` (`AssetMeta`). Assets a version
  points at cannot be deleted.
- **Skills.** `skill_versions_skill_id_checksum_uq` refuses a version whose files a skill already
  has, including an earlier version's; answer with that version. Names follow `SKILL_NAME_RE`
  (`skills_name_ck`).
- **Jobs.** `jobs.workspace_id` stays required, because the contracts' `JobSummary.workspaceId` is
  required and job tokens are bound to their job's workspace. Queue a workspace-less job such as
  `skills.sync` under the workspace it was started from.

## Channels, posts and scheduled tasks

**Channels** (`channels`) are the accounts the publisher posts to. Each belongs to one workspace
(`workspace_id`, since migration `0018`). `series_channels` links series to them (primary key
`(series_id, channel_id)`, with `enabled`) and `api_token_channels` grants them to API clients.
Both carry `workspace_id`, and their composite foreign keys on `(workspace_id, series_id)`,
`(workspace_id, token_id)` and `(workspace_id, channel_id)` (`series_channels_series_fk`,
`series_channels_channel_fk`, `api_token_channels_token_fk`, `api_token_channels_channel_fk`)
keep every link inside one workspace.

- **Credentials** exist only as AES-256-GCM output: `secret_ciphertext` (the encrypted JSON with
  the 16-byte tag appended), `secret_nonce` (12 bytes) and `key_version`. There is no plaintext
  column. The three are set or cleared together (`channels_secret_ck`), the nonce must be 12 bytes
  and the ciphertext longer than the tag. Encryption, decryption and key rotation belong to the
  API's token vault. Never select these columns into a response, a log line or a job payload, and
  derive the contracts' `connected` from `secret_ciphertext is not null`.
- **Status.** An `active` channel has credentials and a `disconnected` one has none
  (`channels_status_secret_ck`), so disconnecting clears the secret columns and sets the status in
  one update. `dry_run` defaults to true and `requires_approval` to false.
- **Accounts.** `channels_platform_external_id_uq` lets a platform account be connected once, so
  it is a channel of one workspace only; planning channels have a null `external_id`. An Instagram
  account published through a Facebook Page points at the Page's channel with `parent_channel_id`
  (set null if the Page is deleted).
- A channel with posts cannot be deleted (`scheduled_posts_channel_id_channels_id_fk`); disable it.
- **Health.** `last_verified_at` is when the daily check last found the credentials valid,
  `last_error` the `PublishError` of the last refusal (cleared by a successful check or
  reconnect), and `rate_limit` the platform's last usage report as a JSON object. None of them
  holds a credential.

**Posts** (`scheduled_posts`) put one item on one channel at one time.

- `scheduled_posts_item_id_channel_id_uq` allows one post per item and channel that is not
  `cancelled`. Insert-or-skip with `target: [itemId, channelId]` and
  ``where: sql`status <> 'cancelled'` ``.
- `version_id` must be a version of the post's item (`scheduled_posts_version_fk`), and `queued`,
  `publishing` and `published` posts must have one (`scheduled_posts_version_ck`). A published
  post has `published_at` (`scheduled_posts_published_at_ck`).
- The contracts' `ScheduledPost` adds joined fields: `workspaceId` from the item, `platform` from
  the channel, and `publishMode` as
  `effectivePublishMode(rules.publishMode, channel.requiresApproval)` with the rules of the series
  format's current version. `dry_run` is stored, fixed at creation.
- `publish_attempts` keeps one row per try (`(post_id, attempt)` unique, from 1). Its `request` is
  stored as given: redact credentials before inserting it.

**Scheduled tasks** (`scheduled_tasks`) are the scheduler's queue. `kind` is text (validate it and
the payload with `scheduledTaskRegistry`); `status` follows `TASK_STATUSES`. Use the helpers in
`src/queries/scheduler.ts`, which take the database or a transaction and an optional `now` for
tests with a fake clock:

- `enqueueTask(db, { kind, payload, runAt?, maxAttempts, dedupeKey?, onDuplicate? })` returns
  `{ task, created }`. A dedupe key is unique among `pending` and `running` tasks
  (`scheduled_tasks_dedupe_key_uq`), so the call is an upsert: by default (`reschedule`) a pending
  duplicate takes the new `runAt`, `payload` and `maxAttempts`, a running one is left alone, and
  `keep` leaves either alone. A finished task frees its key.
- `claimDueTasks(db, { limit, workerId, leaseMs })` takes up to `limit` due tasks in one statement:
  pending tasks whose `run_at` has come and running tasks whose lease ran out, oldest first, through
  a CTE with `FOR UPDATE SKIP LOCKED`. Each becomes `running` with `attempts + 1` and a lease for
  `workerId` (unique per process). A selected task with no attempt left becomes `dead` instead
  (`lease_expired`, or `attempts_exhausted` for a pending one) and is returned in `deadLettered`.
- A run is named by its lease, `taskLease(task, workerId)`: the task id, the worker and the run
  number (`attempts` at claim). `extendLease` renews it and `completeTask` records `succeeded`, a
  retry (`pending` at a new `runAt`), `failed` or `dead`. Both return null once the run has lost
  the task to another claim; stop the handler then.
- `retryTask(db, { id, runAt? })` puts a `failed` or `dead` task back to `pending` with its
  attempts reset. It fails with `23505` on `scheduled_tasks_dedupe_key_uq` when another task holds
  the key.

The partial indexes of these tables compare enum literals (`status <> 'cancelled'`), which is safe
because `post_status` and `task_status` are created, not extended, by the migrations that create
the indexes. A later migration that adds a value to either type must not use it in the same
batch.

## Post metrics

`post_metrics` is the time series of a published post's insights: one row per capture, appended
on the contracts' `insightsSchedule`. A row holds running totals, not deltas, so the latest capture
is the post's current performance.

- `views`, `likes`, `comments`, `shares`, `saves` and `reach` are `bigint` and `avg_watch_ms` an
  `integer`; each is null when the platform does not report it, never negative
  (`post_metrics_counts_ck`). Null is not zero: `aggregatePosts` decides how to count it.
- `raw` is the platform's answer as a JSON object, for metrics without a column. Strip credentials
  before inserting it: Graph API paging links carry an access token.
- `post_metrics_post_id_captured_at_idx` is `(post_id, captured_at desc)`, so a post's history
  newest first (`where post_id = $1 order by captured_at desc`) and the latest capture per post
  come from the index. `latestPostMetrics(db, postIds)` returns that latest row for each post that
  has one (`distinct on (post_id)`); give `aggregatePosts` a `null` for the others.
- The ids are a `bigserial`. Deleting the post deletes its captures.

## OAuth sign-ins and pending connections

Connecting a channel goes through two short-lived tables. Neither stores an OAuth code, a state
or a token in the clear.

**Sign-in states** (`oauth_states`) are written by `oauth.start` and read once by the callback.

- `state_hash` is the SHA-256 of the state sent to the platform, as lowercase hex
  (`oauth_states_state_hash_ck`); the state itself is never stored. It is unique
  (`oauth_states_state_hash_uq`).
- A PKCE code verifier, when the provider uses one, is token-vault output in `pkce_ciphertext`
  (GCM tag appended), `pkce_nonce` (12 bytes) and `key_version`, set or cleared together
  (`oauth_states_pkce_ck`), with the same size checks as the channel columns.
- `redirect_to` is an app path (`oauth_states_redirect_to_ck`: starts with `/`, at most
  `OAUTH_REDIRECT_TO_MAX_LENGTH`); validate it with `OAuthRedirectToSchema` first.
- `expires_at` is `OAUTH_STATE_TTL_MS` (10 minutes) after creation and must be later than
  `created_at`.
- `consumeOAuthState(db, { stateHash, provider, userId, now? })` consumes a state in one
  statement: it must match the hash, provider and user, be unused and unexpired. It returns the
  row with its sealed verifier and leaves it used with the verifier cleared
  (`oauth_states_pkce_used_ck` keeps used states without one). It returns null for an unknown,
  expired, used or foreign state, and concurrent callbacks consume a state at most once. A refusal
  never uses the state up.

**Pending connections** (`oauth_connections`) are written by the callback and accepted once.

- The tokens are sealed with the same columns and format as `channels`: `secret_ciphertext`,
  `secret_nonce` and `key_version`, set or cleared together (`oauth_connections_secret_ck`). Key
  rotation must cover this table too.
- `candidates` is the JSON array of accounts the sign-in offers, at most
  `MAX_CONNECTION_ACCOUNTS` (`oauth_connections_candidates_ck`), each an `OAuthCandidateRow`:
  the contracts' `CandidateAccount` without `alreadyConnected`, which is computed on read. No
  credential goes in it.
- A pending connection has a secret and a consumed one has none
  (`oauth_connections_consumed_ck`). `consumeOAuthConnection(db, { id, userId, now? })` checks the
  user and expiry, sets `consumed_at`, clears the secret and returns the row with the secret it
  had, or null. Call it in the transaction that creates the channels, so a failed accept leaves
  the connection pending.
- `expires_at` is `OAUTH_CONNECTION_TTL_MS` (30 minutes) after the callback.

Both tables cascade from `users`. `purgeExpiredOAuth(db, { now? })` deletes every state and
connection whose `expires_at` has passed, used or not, through `oauth_states_expires_at_idx` and
`oauth_connections_expires_at_idx`, and returns the counts. `provider` is the `oauth_provider` enum,
built from `OAUTH_PROVIDERS`.

## Knowledge-base search

`kb_entries.search` is a stored generated `tsvector`: title (weight A), tags (B), body (C) and
`search_extra` (D). Postgres keeps it current on every insert and update; never write it, and
leave it out of API responses. Put text that should be findable but not shown in `search_extra`;
for references use `referenceSearchExtra({ author, likedReason, transcript })`.

`kbSearch(db, { q, workspaceId?, kinds?, limit? })` returns `KbSearchHit[]` (the contracts shape),
best first:

- **Matching.** `websearch_to_tsquery('english', q)` (so `"exact phrase"`, `-exclude` and `or`
  work), plus trigram matching on the title (`title % q` or `q <% title`, which catches typos)
  and a title prefix match (`title ILIKE q%`, with `%`, `_` and `\` escaped). Soft-deleted
  entries never match.
- **Score.** `ts_rank_cd(search, query, 32)` + `0.6 *` the better of `similarity(title, q)` and
  `word_similarity(q, title)` + `0.3` for a title prefix match. Ties go to the most recently
  updated entry.
- **Snippet.** `ts_headline` over the body with matches between `KB_SNIPPET_MATCH_START` and
  `KB_SNIPPET_MATCH_END`, or the first 160 characters of the body (whitespace collapsed) when the
  body has no match. Sentinel characters stored in a body are stripped first.

An empty query or an empty `kinds` list returns no hits; `limit` is clamped to
`1..KB_SEARCH_MAX_LIMIT`. The trigram thresholds are the `pg_trgm` defaults (0.3 for `%`, 0.6
for `<%`).

## Test harness

Tests run against real Postgres. Each test file gets its own database cloned from a migrated
template, so files run in parallel and never see each other's rows.

- `setupTemplate()` is a vitest globalSetup. It builds `loomcast_template_<hash>`, where the hash
  covers every file in `migrations/`, so worktrees with different migrations never share a
  template. It holds an exclusive advisory lock while building and reuses a complete template
  when one exists. Its teardown drops any `t_*` database a crashed test file left behind.
- `createTestDb()` clones the template into `t_<random>` under a shared advisory lock and returns
  `{ db, url, name, drop }`. Pass `{ empty: true }` for an empty database instead.

Both connect through `TEST_DATABASE_ADMIN_URL` (a role that may create databases, connected to
the `postgres` database). It is read from the environment or the repository's `.env`; CI sets it
directly.

To use the harness in another package:

```ts
// test/global-setup.ts
export { setupTemplate as default } from "@loomcast/db/testing";
```

```ts
// vitest.config.ts: inside defineConfig({ test: { ... } })
globalSetup: ["./test/global-setup.ts"],
```

```ts
// test/workspaces.test.ts
import { createTestDb, type TestDb } from "@loomcast/db/testing";
import { afterAll, beforeAll } from "vitest";

let testDb: TestDb;
beforeAll(async () => {
  testDb = await createTestDb();
});
afterAll(async () => {
  await testDb.drop();
});
```

Old templates are kept, because another worktree may still be using one. To clear them, drop the
`loomcast_template_*` databases you no longer need (`alter database <name> is_template false`
first).
